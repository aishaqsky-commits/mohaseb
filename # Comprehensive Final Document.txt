## 1. Vision and Scope

### 1.1 Application Description

A full-stack, smart accounting application designed for goods and services merchants, built on solid accounting principles. It records double-entry bookkeeping (debit/credit) behind intuitive, easy-to-understand buttons for non-accountants. It features an AI agent capable of understanding text and voice descriptions in colloquial dialects, supports offline operations with cross-device synchronization for a single account, and is highly scalable up to 5 million users.

### 1.2 Target Audience

* Retail merchants (shops, stalls, small warehouses)
* Service providers (electricians, plumbers, consultants, etc.)
* Small and Medium Enterprises (SMEs) in Yemen and the Arab World

### 1.3 Core Principles

| Principle | Implementation |
| --- | --- |
| **Simplicity of Use** | Every operation = 1 Button / Simple Wizard. Accounting jargon only appears in an optional advanced mode. |
| **Accounting Accuracy** | Every journal entry is forced to balance (SUM Debit = SUM Credit) at the database constraint level. |
| **Offline-Capable** | Local-First architecture using local SQLite + eventual synchronization. |
| **Multi-Tenant Isolation** | Multi-tenancy from day one (every company = an isolated Tenant). |
| **Transparency** | AI never posts an entry automatically; explicit user confirmation is always required. |

## 2. Architectural Philosophy and Governing Principles

### 2.1 Overall Design Pattern

**Local-First + Offline-First Architecture**

* The local database (SQLite via Drift/SQLCipher) is the immediate source of truth.
* Every operation is written locally first, then appended to a `sync_queue` to sync when the internet is available.
* Synchronization uses an `operation_id` (UUID) to ensure idempotency and prevent duplication.
* Conflict Resolution: Last-Write-Wins for metadata, Append-only for financial journal entries.

### 2.2 Backend Pattern

**Modular Monolith** designed to easily break into Microservices later:

* `accounting` — The journal entry engine (the core)
* `inventory` — Stock and items
* `contacts` — Customers/Suppliers
* `hr-payroll` — Employees and payroll
* `ai-gateway` — Intermediate AI routing layer
* `reports` — Reporting and exports
* `sync` — Synchronization service
* `notifications` — Alerts (Push/SMS/WhatsApp)

### 2.3 Non-Negotiable Engineering Principles

1. **Double-Entry Integrity:** Every accounting entry MUST have matching debits and credits, enforced via a DB constraint.
2. **Immutability for Posted Entries:** No direct editing of a posted entry. Corrections are made strictly via a Reversal Entry.
3. **Row-Level Security (RLS):** Strict isolation of company data (Tenant) at the PostgreSQL level, not just via middleware.
4. **Human-in-the-Loop:** Any AI suggestion requires explicit user confirmation before saving.
5. **API-First:** The backend is built as a REST API documented with OpenAPI before building any UI screens.
6. **UUID Keys:** All tables use UUID v7 (or BIGINT with public_id) to support offline record creation seamlessly.

-- Trigger: Enforce Double-Entry Balance before Commit
CREATE OR REPLACE FUNCTION fn_validate_journal_balance() RETURNS TRIGGER AS $$
DECLARE
total_debit NUMERIC(18,4);
total_credit NUMERIC(18,4);
BEGIN
SELECT COALESCE(SUM(debit),0), COALESCE(SUM(credit),0)
INTO total_debit, total_credit
FROM journal_entry_lines
WHERE journal_entry_id = NEW.journal_entry_id;

IF total_debit <> total_credit THEN
RAISE EXCEPTION 'Unbalanced Entry: Debit % != Credit %', total_debit, total_credit;
END IF;
RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE CONSTRAINT TRIGGER trg_validate_balance
AFTER INSERT OR UPDATE ON journal_entry_lines
DEFERRABLE INITIALLY DEFERRED
FOR EACH ROW EXECUTE FUNCTION fn_validate_journal_balance();

-- Trigger: Prevent editing of a posted entry
CREATE OR REPLACE FUNCTION fn_prevent_posted_edit() RETURNS TRIGGER AS $$
BEGIN
IF OLD.status = 'posted' THEN
RAISE EXCEPTION 'Cannot edit a posted entry. Use a reversal entry instead.';
END IF;
RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_prevent_edit
BEFORE UPDATE OR DELETE ON journal_entries
FOR EACH ROW EXECUTE FUNCTION fn_prevent_posted_edit();

## 5. Role-Based Access Control (RBAC) Model

### 5.1 Roles within the Merchant App (Tenant-Level)

| Role | Core Permissions | Restrictions |
| --- | --- | --- |
| **Owner** | Everything, including deleting the company, managing subscriptions, and inviting users. | Cannot be deleted from the system. |
| **Accountant** | Journal entries, financial reports, chart of accounts, auditing. | Cannot delete the company. |
| **Sales Staff** | Register sales, read-only inventory view. | Cannot view financial reports. |
| **Inventory Staff** | Manage items, stock adjustments, inventory count. | Cannot execute direct sales. |
| **Cashier** | Cash collection/payments only, cannot edit posted entries. | Subject to configurable amount limits. |
| **Viewer** | Read-only across the board. | No modification rights. |
| **Custom Role** | Built by the Owner from the permissions matrix. | Flexible. |

## 7. AI Layer

### 7.1 AI Gateway Components

* **NLU Engine:** Converts Text/Voice into Intents + Entities (Amount, Party, Date).
* **Posting Agent:** Proposes a Draft Journal Entry — explicit user confirmation required.
* **Analytics Agent:** Answers data queries (sales, growth, debts).
* **Advisor Agent:** Provides accounting/financial consultation via RAG over the knowledge base + user data.
* **Onboarding Agent:** Guides the user step-by-step on how to use the app.

### 7.2 Mandatory Safeguards

* **Function Calling:** The model strictly calls defined functions (`propose_journal_entry`, `get_sales_report`, etc.), not raw free-form SQL.
* **Read-Only Guardrails:** Data queries pass through a secure layer (Whitelisted Views).
* **Human-in-the-Loop:** No entry is automatically posted by AI.
* **Key Management:** AES-256 encryption before storage, decrypted in memory only, never written to logs.
* **Multi-Provider:** Adapter Pattern supports OpenAI, Anthropic, Gemini, Ollama, allowing seamless provider switching without code changes.

---

## 8. Synchronization and Offline Mode

* **Mechanism:** Simplified Event Sourcing via `sync_queue` using `operation_id` for Idempotency.
* **Conflict Strategy:** Last-Write-Wins for metadata, Append-only for financial entries.
* **Frequency:** Background sync upon connection + manual sync button + WebSockets for real-time updates between devices on the same account.
* **Offline UI:** All buttons and saved reports function fully offline; records are cached locally and uploaded upon reconnection.

## 10. Quality and Security Standards (Definition of Done)

A feature is considered "Done" only if:

1. ✅ It matches the functional requirement.
2. ✅ Unit + Integration tests pass (Coverage ≥ 80% for the accounting module, ≥ 60% for the rest).
3. ✅ It works offline (if related to local data).
4. ✅ Full support for RTL and the Arabic language.
5. ✅ Fully documented (OpenAPI + code comments).
6. ✅ Code Review completed by a second party.
7. ✅ No previously passing tests are broken (Regression).
8. ✅ Basic security review passed (Tenant isolation, no exposed keys, no data leaks).
9. ✅ Journal balancing trigger successfully fires for all templates.

### 10.1 Mandatory Security Checklist

* [ ] Local database encryption (SQLCipher).
* [ ] TLS 1.3 for all communications.
* [ ] Rate Limiting on Auth and AI endpoints.
* [ ] RBAC enforcement on every Module/Action.
* [ ] Append-only Audit Log for every financial operation.
* [ ] `tenant_id` isolation via RLS at the PostgreSQL level.
* [ ] Automated daily backups + monthly restoration testing.
